Next.js 개발자를 위한 TanStack Start 멘탈 모델

https://www.adarsha.dev/blog/tanstack-mental-model-for-nextjs-developers

Next.js와 TanStack Start의 차이를 기능 비교가 아니라 '무엇을 기본값으로 두는가'로 풀어낸 글입니다. 글이 경고하는 isomorphic 로더와 서버 함수 경계 문제가 실제로 터진 사례가 LY corp 컨퍼런스의 Version Skew 이야기입니다. 경계를 명시하지 않으면 client와 server 함수 연결이 어떻게 깨지는지 같이 보면 좋습니다. 추가로 TanStack Start보단 느리지만 안정적이고 loader-component-action 패턴을 지향하는 React Router도 함께 관찰할 만합니다. 머잖아, TanStack Start가 Next.js가 될지도요.

LLM이 "하게" 만드는 것보다 "못 하게" 만드는 게 더 좋다

https://polar.sh/blog/orbit-llm-safe-design-system

디자인 시스템을 '지키길 바라는 가이드라인'에서 '어기는 게 불가능한 제약'으로 옮긴 사례입니다. 지난 호에서 다룬 "LLM 친화"는 어떻게 달성되고 있는가를 결국 무엇으로 이루는지, 그 한 가지 구체적인 답이 잘못된 값을 타입과 토큰으로 아예 표현 불가능하게 만드는 이 방식입니다. tailwind 대신 토큰 기반 CSS-in-JS를 선택한 이유도 다양하게 풀어내고 있으니 스타일링에 고민이신 분들은 한 번 보시길 추천드립니다.

TanStack Table v9, 무엇을 다시 짜나

https://tanstack.com/blog/tanstack-table-v9-typescript-performance

큰 표를 다루는 라이브러리가 결국 부딪히는 벽은 대용량을 어떻게 버티느냐입니다. List Virtualization, 심화버전, 그리고 Diff 빠르게 보여주기를 같이 보면, 가상화로 보이는 행을 줄이고도 남는 메모리와 재렌더 비용을 라이브러리 차원에서 어떻게 깎는지가 보입니다. 또한, DX를 최적화하려다 만난 문제가 Tanstack Router의 TypeScript 성능 최적화하기와 같은 문제를 갖고 있으므로, 라이브러리 개발자에게 무엇보다도 중요한 부분이라고 생각합니다.

App Router로 느린 응답을 80% 줄이기까지

https://dev.to/subito/how-we-cut-slow-responses-by-80-migrating-to-nextjs-app-router-37da

RSC와 스트리밍이 응답을 빠르게 한다는 얘기는 많지만, 실제로 무엇이 빨라지고 어디서 막히는지는 따로 봐야 합니다. 여러 글에서 RSC를 RSC 또한 폭포 요청 문제가 있다, Conductor의 Rewrite 중 무엇이 성능을 높였나로 다뤘는데, 이 글은 그 이론이 한 서비스의 프로덕션에서 어떤 인프라 벽에 부딪히는지, 그리고 프레임워크, 런타임, CDN, 모니터링이 한 몸이 되어 구동 방식을 일치해야 성능 이득이 실현된다는 사실도 보여줍니다.
