2:T698,/kudzu-based-bench/assets/notion/9fc7ff5cfb7d7e7d.png3:T1bb9,<h2 data-notion-block-id="842c4496-9e4f-46fe-b24c-ea868549e437" id="842c4496-9e4f-46fe-b24c-ea868549e437">않이 그래서 인증 토큰을 어디에 저장해야하는거죠?</h2><a href="https://auth0.com/blog/secure-browser-storage-the-facts" class="bookmark-link" target="_blank" rel="noreferrer">https://auth0.com/blog/secure-browser-storage-the-facts</a><p data-notion-block-id="b827c904-52ad-4f2e-8b50-e6c8d71354a3"><b>심윤섭</b>: 프로그램을 개발하는 이상 보안에 신경써야 합니다. 나만의 작고 소중한 서비스의 사용자들의 정보를 지켜야 하니까요. 그래서 서비스를 만드는 프론트엔드 개발자는 항상 인증이 완료된 토큰을 어디에 저장할지 걱정합니다. 갖고온 글은 토큰의 저장 방식을 명확하게 정해주는 글이 아닙니다. 오히려 "너가 뭘 생각했든 그 방식은 위험할 수 있어."를 알려주는 글에 가깝죠(<code>Web Worker</code>를 사용한 방식을 몰랐다면 말이죠!). 글의 마무리는 "<code>Web Worker</code>를 사용해서 사용자가 인메모리 변수에 접근할 수 없게 하거나, 우리 서비스를 사용해!"로 끝나지만 우리들의 클라이언트인 기획자는 만만하지 않습니다. "로그인 유지 기능"을 구현해달라고 요청이 들어왔다고 가정하죠. 이 기능을 구현하기 위해 <code>Web Storage</code> 중 하나에 저장해야 하고, 결국 위험에 노출될 수 밖에 없습니다. "그럼 어떻게 하죠?"라고 물어보면 "다 위험하니까 쓰지 마라"라고 할 수는 없습니다. 그것을 전해주려고 글을 가져온 것도 아니구요. 제가 생각하는 결론은 "<b>무엇을 쓰던간 위험에 노출될 수 있다는 것은 인지하고, XSS는 막는 방법을 알아보는게 좋다</b>"입니다. 모든 문제에 은탄환은 없으니까요.</p><p data-notion-block-id="1e39d40a-b6d6-46ab-9cba-1331406a8208"><b>최원빈</b>: 공격 방식을 이해하는 것이 인상깊은 글입니다. cookie 보다는 <code>localStoarge</code>가 안정적이고, 그보다는 <code>sessionStoarge</code>가 더 안정적이고, 그보다는 <code>httpOnly</code> 쿠키가 안정적이라는 것은 상식이며 사실이지만, 결국 공격을 의도한다면 어렵지 않게 단순한 공격(XSS)으로 접근이 가능하다는 사실을 충분히 인지해야 한다고 생각해요. 이런 위험을 인지하고 있다면, 폼 관련 기능을 개발할 때 이를 방지해야 한다는걸 잊지 않을 수 있을 것 같네요. 최선의 방어는 공격이라는 점을 다시 한번 깨우치고 갑니다. 😲</p><h2 data-notion-block-id="9e5bb35f-15dd-4263-a1f5-252937acdbc6" id="9e5bb35f-15dd-4263-a1f5-252937acdbc6">React에서 polymorpic component 만들기(w. asChild)</h2><a href="https://www.jacobparis.com/content/react-as-child" class="bookmark-link" target="_blank" rel="noreferrer">https://www.jacobparis.com/content/react-as-child</a><p data-notion-block-id="3fc18037-f831-4bfb-a36a-eba4d84856eb"><b>심윤섭</b>:  보통 디자인 시스템을 마련할 때에 많은 것을 고려해야 합니다. 그 중에서는 컴포넌트를 커스텀하기 쉽게 하는 것도 그 중 하나라고 생각합니다. Button 스타일이 <code>&#x3C;button></code>태그에만 쓰이지만 않고 <code>&#x3C;a></code>태그나 다른 커스텀 컴포넌트에도 사용되니까요. 이 때 많이 사용되는 방법이 Chakra UI의 <code>as</code> props, MUI의 <code>component</code> props 같이 element 이름이나 컴포넌트 자체를 넘기는 방법입니다. 이를 사용하는 방법은 <a href="https://blog.logrocket.com/build-strongly-typed-polymorphic-components-react-typescript">자세하게 TypeScript 구현하는 글</a> (<a href="https://kciter.so/posts/polymorphic-react-component">한국어로 쓰여진 글(번역 아님)</a>도 있네요!)를 참고하세요. 하지만 이 기사는 Radix의 `asChild`(next/link의 <code>passHref</code>와 비슷할지도요)에 주목하고 이를 구현하는 방법을 설명합니다. 디자인 시스템을 만드는 사람이라면 꼭 보셨으면 합니다!</p><p data-notion-block-id="e49124ea-b045-46b8-9000-51e047e0576d"><b>최원빈</b>: <a href="https://www.radix-ui.com/">Radix UI</a>는 자유도 높은 디자인 시스템을 구현하기 위해 <code>asChild</code> 패턴, <code>Compound</code> 패턴 등을 적절히 사용해 Headless한 라이브러리의 우수 사례를 만들었다고 생각합니다. 접근성도 충분히 고려해 라이브러리를 사용하는 것 만으로도 배울 점이 많은데, <code>asChild</code>패턴을 구현하며 주된 환경인 TypeScript + React 에서 React Element와 HTML Element 사이의 갭을 메꿔나가는 과정이 흥미롭네요. 컴포넌트의 추상화가 중요시되는 가운데, leaf 노드에 가까운 컴포넌트를 추상화하려면 분명히 알아야 할 점이라고 생각하기에 추천합니다.</p><h2 data-notion-block-id="3107fecb-1574-47c1-94f0-f1a53442a6a4"
