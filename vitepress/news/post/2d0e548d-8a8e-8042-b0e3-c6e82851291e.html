Beyond the Article: 한 걸음 더

React Aria, shadcn registry에 참가하다.

https://react-aria.adobe.com/

React aria가 새로운 docs로 재편하면서 React spectrum은 marcos를 활용한 version 2를 출시했고, React aria는 shadcn을 활용한 컴포넌트 추가 방식을 활용했습니다. 이전에 소개한 shadcn create( 한국어 소개 번역글 )같이, React aria또한 자신만의 컴포넌트 라이브러리로 만들 수 있게 돕기 때문에(ex. npx shadcn add @react-aria/css-button, npx shadcn add @react-aria/tailwind-button, 물론 css 방식은 shadcn의 철학과는 약간 거리가 있습니다) shadcn create에서 제공하는 Radix UI, Base UI 기반 컴포넌트 외에도 다른 방식으로 라이브러리를 만들 수 있음을 보여줍니다. 이외에도 여러 등록된 라이브러리가 많으니 자신의 어플리케이션에 맞게 적용해보는 것을 추천드립니다.

RSC는 잘 구현하면 성능적으로 최고다.

https://calendar.perfplanet.com/2025/intro-to-performance-of-react-server-components/

RSC를 이상적인 어플리케이션에서는 CSR, SSR(Client data fetching, Server data fetching)보다 좋은 성능을 낸다는 것을 보여주는 글입니다. 하지만 역시, RSC 구현방식이 프레임워크마다 다르므로, 특정 프레임워크에 종속될 수도 있다는 점, 그리고 최근 사태처럼 아직까지는 불안정한 모습을 보여준다는 점을 보여주고 있습니다. React Router나 Tanstack start에서도 구현할 수는 있다는 점은 긍정적으로 검토해봐도 있겠습니다.

어쩌면 AI가 발전하면서, 프로토타입이 새로운 PRD가 될 수도 있다.

https://www.figma.com/blog/prototypes-are-the-new-prds/

어떻게 보면 Figma make를 홍보하는 글일 수도 있겠지만, 추후에는 초기 아이디어가 PRD로 만드는 것이 아니라 Figma make나 Stitch같은 AI 기반 프롬포트로 만드는 디자인 툴이 진실의 원천으로 통합될 수도 있겠다는 관점을 줄 수 있는 글입니다.

번들러는, 이제 속도보다 다른 부분을 신경써야 한다

https://redmonk.com/kholterhoff/2025/12/16/javascript-bundler-grand-prix/

번들러의 속도는 Parcel부터 시작해서 다른 언어로 이루어진 ESBuild, Bun, … 여러가지 엄청나게 빠른 번들러들이 많이 나왔습니다. 하지만 Tree shaking방식(번들러마다 Tree shaking은 어떻게 다를까)부터 시작해서 통합 툴을 지원하거나, 특별한 기능을 지원하는 등 여러가지 특징을 가지고 있습니다. 그래서 이제, 번들러의 속도는 한계까지 빨라졌기에, 여러가지 특징이나, 혹은 글에서 나온 것처럼, 빌드 결과물 크기가 얼마나 클지(ex. minification benchmark)에 대해 경쟁할 수도 있습니다. 미래는 아무것도 모르겠죠.
