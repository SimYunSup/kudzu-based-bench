    단순함이 최고다.

    https://blog.webf.zone/why-next-js-falls-short-on-software-engineering-d3575614bd08

    Next.js가 아키텍쳐 관점에서 왜 부족한지 소개하는 글입니다. 물론 Next.js는 기능적인 측면에서 메타프레임워크 중에서 많은 것을 제공하는 편에 속합니다. 수많은 Next.js를 싫어하는 사람의 글(왜 나는 Next.js가 아니라 Astro를 선택했을까?, Next.js에서 Astro로 변경하기, …) 중 하나이지만, 복잡성과 컴파일러 관점에서, 그리고 확장성 관점에서, 또한 결합 관점에서 Next.js를 살펴보면서 Next.js는 많은 것을 제공하지만 다른 스택을 검토할 것을 저자는 권장하는 것에 어느정도 동의해서 글을 가져왔습니다. Next.js 16의 adapter 구현, 그리고 OpenNext의 구현의 도움으로 Next.js가 개방적인 프레임워크로 움직이려고 하고 있지만, 아직 Nuxt.js나 Astro보다는 덜하다는 것은 인지해야 할 것입니다. 저자의 단순함을 옹호하는 것은 매우 동의합니다. 물론 이유가 있는 경우 복잡함을 추가하거나 아키텍쳐를 구축해야겠지만, 그렇지 않다면 단순히 인지부하를 추가하는 것일테니까요.

    제약과 규율의 차이

    https://cekrem.github.io/posts/the-discipline-of-constraints-elm-usereducer-lessons/

    Elm에서는 제약으로 제한되어있던 것이, React에서는 풀어져있기에 규율을 가져와서 습관화해야 한다는 것을 알려주는 글입니다. 최근에는 React의 공식문서나, 혹은 메타 프레임워크나 라이브러리를 통해 규율을 활성화하기도 합니다. 그렇기에, 좋은 코드베이스는 어떤 규율을 채용하고 있나 살펴보는 것도 방법이 될 것 같습니다. 최근의 useEffect를 잘못 사용해서 Cloudflare에서의 서비스 중단이 이루어진 것을 생각하면, 규율을 활성화하는 것은 물론이고, 체화까지 해야할 것 같습니다(아직 컴파일러는 대체가 될 수는 없습니다.).

    HTTP 캐싱 가이드

    https://www.jonoalderson.com/performance/http-caching/

    useSyncExternalStore()과 동시 렌더링

    https://kurtextrem.de/posts/react-uses-hydration

    React 시스템에서 벗어난 시스템을 제공하는 방법을 도와주는 useSyncExternalStore()을 통해 SSR을 판단하는 시스템의 어느 부분이 잘못되었는지 확인하고, 어떻게 해결할 수 있는지 해결책을 보여주는 간단한 글입니다. 하지만 이해하기 힘든 React에서 상태 불일치를 소개하므로, 해당 글도 참고하세요.
