    Beyond the Article: 한 걸음 더

    우리가 프레임워크의 근간을 배워야 하는 이유

    https://saschb2b.com/ko/blog/flight-protocol-dos

    React Server Components 관련 취약점 중에서 Flight 프로토콜이 왜 문제가 되었는지 Flight 프로토콜이 무엇인지를 바탕으로 소개하는 글이자, 프레임워크에서 문서를 제공하는, 그리고 주로 보여주는 API만 아는 것만이 끝이 아님을 소개하는 글입니다. 가장 처음 발견된 RSC관련 취약점인 React2Shell(React2Shell 발견기, 2)또한 Flight 프로토콜 기반 취약점이므로, 이 글의 마지막인 tRPC/GraphQL/Websocket의 경계에도 적용되므로 프레임워크/프로토콜 또한 우리가 알아야 함을 간접적으로 보여줍니다.

    AI에 대한 시니어 개발자의 생각

    https://blog.isquaredsoftware.com/2026/05/ai-thoughts-part-1-fears-opinions-journey/

    Redux 메인테이너 마크 에릭슨이 쓴 12,000자짜리 글입니다. 25년차 개발자가 AI 앞에서 자기도 한동안 무너졌었다고 고백하는 글로, 거부하다가, 가벼운 우울의 시기를 지나고, 마지못해 받아들이고, 그런데도 "내 두려움 대부분은 지금도 여전히 유효하다"고 끝내 못 박습니다. 정보 전달이 공짜가 된 시대에, 정보를 주려는 글은 AI와 같은 트랙에서 경쟁하다 집니다. 좋은 글이 주던 가치는 원래 그 옆에 붙은 것들, 판단과 증언과 방향이었고, 이건 AI한테 물어볼 수 없는 것들입니다.

    jotai를 정확하게 사용하는 방법

    https://www.peterp.me/articles/jotai-structural-sharing-vs-selectatom/

    jotai의 파생 atom이 어떻게 동작하는지, 그리고 언제 문제가 되는지 살펴보는 글입니다. Object.is는 React.memo에도 쓰이므로(React.memo를 더 빠르게), 파생 값을 생성할 때 어느 방식이 좋은지 한 번 더 생각하게 만드는 글이므로, jotai를 사용하지 않더라도 파생 값을 많이 사용한다면 보시길 추천드립니다.

    빠른 어플리케이션은 최신 데이터를 보여주지 않는다.

    https://github.blog/engineering/architecture-optimization/from-latency-to-instant-modernizing-github-issues-navigation-performance/https://performance.dev/how-is-linear-so-fast-a-technical-breakdown

    첫번째 글은 GitHub Issues 팀이 Rails/React가 섞인 기존 구조를 통째로 다시 짜지 않고, IndexedDB 클라이언트 캐시와 stale-while-revalidate, service worker만으로 페이지 이동을 즉각적으로 느끼게 만든 과정을 단계별로 소개하는 글입니다. 두번째 글은 Linear의 속도가 어디서 나오는지 전반을 뜯어보는 글입니다. 서버를 정답의 출처가 아니라 동기화 대상으로 두고 모든 것을 로컬에서 먼저 처리한다는 한 번의 결정이, 어떻게 CSR 앱을 SSR보다 빠르게 느껴지게 만드는지 보시면 좋습니다. sync engine 자체가 궁금하시다면 Sync Engine이 그리는 미래를, 마지막 애니메이션 파트는 애니메이션은 항상 필요하지 않다와 함께 보시면 좋습니다. 두 글 모두 대용량 데이터를 어떻게 빠르게 보여줄 수 있었는지 접근 방식을 다르게 보여주므로, 상황에 맞게 사용하시는 것을 추천드립니다.
